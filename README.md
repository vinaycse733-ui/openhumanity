# OpenHumanity

Knowledge belongs to everyone.

An experimental knowledge commons with portable, source-backed claims and content-addressed revisions.

## Install and run v0.1.0rc1

Python 3.11+ is required. Clone the repository and run:

```sh
python -m venv .venv
# Activate the virtual environment for your platform.
python -m pip install .
openhumanity keygen identity.pem
openhumanity-web --key identity.pem --db node.sqlite
```

Open http://127.0.0.1:8000 in a browser. The server listens only on loopback. Do not expose it through port forwarding or a public reverse proxy. Keep private keys and database files in a restricted local directory. Do not run a generic static file server from the repository root; it may expose those files. The older index.html is an unsigned browser-only experiment, not the signed node application.

## Tests
`python -m unittest discover -s tests -v`

## Signed node quickstart
Install Python 3.11+ and run:

```sh
python -m pip install -r requirements.txt
python node_cli.py keygen identity.pem
python node_cli.py --db shared.sqlite add --key identity.pem --source https://example.org "Example claim"
python node_cli.py --db shared.sqlite export example.bundle.json
python node_cli.py --db second.sqlite import example.bundle.json
python node_cli.py --db second.sqlite search Example
```

Keys generated by this version are encrypted PEM files. Raw keys from earlier versions are not accepted by the new CLI. Keep backups securely; the application cannot recover forgotten passphrases.

## Verify local data
Run `openhumanity --db node.sqlite doctor` against an existing database to check SQLite structure, record signatures, record identifiers and revision dependencies. This cannot establish the truth of claims or detect deletion of complete independent revision chains. Diagnostics reject missing database paths.

Create a verified database snapshot with `openhumanity --db node.sqlite backup backup.sqlite`. The destination must not already exist. The backup is checked for SQLite and signed-record integrity before success is reported. Keep the database backup and encrypted identity key separately secured; database contents are not encrypted. To restore, stop node processes and open the verified snapshot as a separate database before replacing any live files.

## Peer exchange
In one terminal, explicitly serve a database containing only records intended for sharing:
```sh
python peer.py --db shared.sqlite serve
```
In another:
```sh
python peer.py --db second.sqlite pull http://127.0.0.1:8765
```
Remote pulls require HTTPS. Serving remotely requires a separately configured TLS reverse proxy and access controls. The local peer endpoint only accepts a single loopback Host header with the listening port and rejects browser-origin requests. An independently secured reverse proxy would need to rewrite Host to that loopback value; remote proxy operation is not tested. Local HTTP pulls bypass environment proxies. The server exports the entire selected database, has no authentication, and is not suitable for direct internet exposure. Exchange is manual and limited to 1000 records and 8 MiB per network bundle. CLI file export/import is limited to 1000 records and 64 MiB; larger databases require a future paginated exchange implementation. No automatic discovery or pagination yet. The dedicated node_web.py browser UI uses signed node storage. The older index.html is separate.
