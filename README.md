# OpenHumanity

Knowledge belongs to everyone.

An experimental, model-independent AI evidence layer with portable, source-backed claims, signed evidence and content-addressed revisions. It reports provenance and disagreement, not automatic truth.

## Install and run v0.2 development build

Python 3.11+ is required. Clone the repository and run:

```sh
python -m venv .venv
# Activate the virtual environment for your platform.
python -m pip install .
openhumanity keygen identity.pem
openhumanity-web --key identity.pem --db node.sqlite
```

Open http://127.0.0.1:8000 in a browser. The server listens only on loopback. Do not expose it through port forwarding or a public reverse proxy. Keep private keys and database files in a restricted local directory. Do not run a generic static file server from the repository root; it may expose those files. The older index.html is an unsigned browser-only experiment, not the signed node application.

## Tests
`python -m unittest discover -s tests -v`

## Signed node quickstart
Install Python 3.11+ and run:

```sh
python -m pip install -r requirements.txt
python node_cli.py keygen identity.pem
python node_cli.py --db shared.sqlite add --key identity.pem --source https://example.org "Example claim"
python node_cli.py --db shared.sqlite export example.bundle.json
python node_cli.py --db second.sqlite import example.bundle.json
python node_cli.py --db second.sqlite search Example
```

Keys generated by this version are encrypted PEM files. Raw keys from earlier versions are not accepted by the new CLI. Keep backups securely; the application cannot recover forgotten passphrases.

## Verify local data
Run `openhumanity --db node.sqlite doctor` against an existing database to check SQLite structure, record signatures, record identifiers and revision dependencies. This cannot establish the truth of claims or detect deletion of complete independent revision chains. Diagnostics reject missing database paths.

Create a verified database snapshot with `openhumanity --db node.sqlite backup backup.sqlite`. The destination must not already exist. The backup is checked for SQLite and signed-record integrity before success is reported. Keep the database backup and encrypted identity key separately secured; database contents are not encrypted. To restore, stop node processes and open the verified snapshot as a separate database before replacing any live files.

## Peer exchange
In one terminal, explicitly serve a database containing only records intended for sharing:
```sh
python peer.py --db shared.sqlite serve
```
In another:
```sh
python peer.py --db second.sqlite pull http://127.0.0.1:8765
```
Remote pulls require HTTPS. Serving remotely requires a separately configured TLS reverse proxy and access controls. The local peer endpoint only accepts a single loopback Host header with the listening port and rejects browser-origin requests. An independently secured reverse proxy would need to rewrite Host to that loopback value; remote proxy operation is not tested. Local HTTP pulls bypass environment proxies. The server exports the entire selected database, has no authentication, and is not suitable for direct internet exposure. Exchange is manual and limited to 1000 records and 8 MiB per network bundle. CLI file export/import is limited to 1000 records and 64 MiB; larger databases require a future paginated exchange implementation. No automatic discovery or pagination yet. The dedicated node_web.py browser UI uses signed node storage. The older index.html is separate.

## AI evidence layer

Create a claim using the signed node CLI, then use its returned identifier:

```sh
openhumanity-trust --db node.sqlite evidence CLAIM_ID supports "Relevant excerpt" --source https://example.org --key identity.pem
openhumanity-trust --db node.sqlite report CLAIM_ID
```

Use `contradicts` or `context` for other evidence relationships. The report groups evidence by contributor-asserted relationship, includes signed envelopes and always sets truth_status to not_determined. Use repeated --trusted-key arguments to mark keys you trust locally; this is not a guarantee of factual accuracy. Source contents are not fetched or checked.

With the local browser node running, GET http://127.0.0.1:8000/v1/claims/CLAIM_ID/report returns the same report without caller trust preferences. Keep the API local. It is not a hosted AI service. See TRUST_PROTOCOL.md for the compatibility and security contract.

## Browser evidence review

Select Review evidence on a claim to view supporting, contradictory and contextual evidence, distinct record counts and signed record details. The page does not check publisher proofs; use the client with a local publisher policy for that. All local read routes reject foreign Origin headers and browser requests marked cross-site or same-site rather than same-origin. Open the local address directly.

## Browser evidence authoring

Use Add evidence in the local browser interface, enter a claim's record ID, choose supports, contradicts or context, and enter the excerpt and sources. The node signs the evidence with the unlocked local key. These are v2 evidence records; use the CLI with --snapshot for v3 signed source-file fingerprints. The browser never retrieves source URLs. Choose Review evidence on a claim to see supporting, contradictory and contextual records, source fingerprints and signature details. Publisher proofs are not checked in the browser view.

## Local AI application client

With the browser node running, execute `openhumanity-client CLAIM_ID --port 8000` or call `trust_client.fetch_verified_report(claim_id, port=8000)` from a Python application. It connects only to IPv4 loopback, rejects redirects, bypasses environment proxies, bounds the response and independently verifies signed evidence. The application must choose the expected claim ID and treat report content as untrusted data. No model-provider invocation or automatic source retrieval is performed.

## Optional local AI model integration

If you already run Ollama on this computer with a downloaded local model, and the signed browser node is running, use:

```sh
openhumanity-ask CLAIM_ID "What does the evidence say?" --model YOUR_LOCAL_MODEL
```

The command retrieves and independently verifies the report, explicitly sends the report and question to the loopback Ollama-compatible /api/chat endpoint, and validates returned citation IDs against the supplied evidence. It requests JSON output with no tools, bounds input and response sizes, refuses redirects and bypasses environment proxies. It does not download or install models, or make cloud API calls itself. Use a genuinely local model and a trusted runtime configuration that does not forward data to the cloud. The model may still misinterpret evidence, follow malicious text, omit disagreement or produce unsupported claims. Citation IDs being valid does not establish entailment. Output is labeled model_generated_not_fact_checked. The application also returns an independently constructed evidence_index and uncited_evidence_ids grouped by relationship, plus conflicting_evidence_present. Display these separately from the generated answer so that omitted disagreement remains visible. These fields reflect contributor assertions in the available report, not verified truth. Real inference has not been tested yet; integration tests use a controlled HTTP response fixture, not a language model.

## Optional AI summarization (experimental)

With the local signed node running and an already-installed model in a trusted Ollama runtime, run:

```sh
openhumanity-ai CLAIM_ID "What evidence supports or contradicts this claim?" --model YOUR_LOCAL_MODEL
```

The adapter fetches a verified report and submits its contents and your question to the configured loopback Ollama endpoint. It does not install models, use tools, fetch source URLs or follow HTTP redirects. Only use a runtime and model you have independently configured for local inference; the adapter cannot guarantee the runtime will not forward data to a cloud provider. The model receives claim and evidence text, so only submit data you are authorized to share with that runtime.

The adapter rejects invalid citation identifiers, missing citations when evidence exists, incomplete responses and oversized requests. Both AI commands preserve an evidence_index, uncited_evidence_ids and conflicting_evidence_present independently of the generated answer; display these alongside the model summary. Citation membership does not establish that the model's prose follows the evidence. The generated text is unverified, vulnerable to prompt injection and not a truth verdict. Model-specific context limits may be smaller than the adapter's byte limit. Real model inference has not yet been tested; HTTP-contract tests use a test server, not a model.

## Real model smoke check

With an already-installed model and trusted local Ollama runtime running, execute:

```sh
openhumanity-model-smoke --model YOUR_LOCAL_MODEL
```

This creates a disposable in-memory node with fictional supporting and contradictory evidence, retrieves and independently verifies its report, and makes a real local model request. It does not use your database, install models or fetch URLs. A successful run checks response structure, citation identifiers and deterministic evidence coverage; it does not certify the model's factual accuracy or resistance to prompt injection. A missing runtime fails explicitly. Both model commands preserve uncited conflicting evidence separately from generated text.

## Real inference smoke check

With a trusted Ollama runtime already running locally and a model already installed, run `openhumanity-model-smoke --model YOUR_LOCAL_MODEL`. The command creates an isolated in-memory node with synthetic conflicting evidence; it does not access your knowledge database or download any model. A successful run demonstrates that the configured runtime returned a parseable response with valid citation identifiers, not factual accuracy or robust resistance to prompt injection. A controlled HTTP fixture exercises the workflow in automated tests; it is not real model inference.

## Developer SDK

```python
from trust_sdk import verify_report, check_excerpt

# payload: a parsed report received from a node.
# expected_claim_id: the identifier requested by your application.
verified = verify_report(payload, expected_claim_id)
quotation = check_excerpt(source_bytes, excerpt, expected_sha256)
```

The SDK verifies signed records and recomputes evidence counts. Source bytes and any expected digest must be independently obtained by the caller. A quotation match does not prove source authenticity or factual accuracy. Use the optional `--snapshot source.txt` argument on the evidence command to sign a source fingerprint after an exact quotation check. Supply exactly one `--source`. `trust_sdk.verify_snapshot(envelope, source_bytes)` verifies the signed binding. Source bytes remain outside the database and must be retained separately. Neither the CLI nor SDK establishes that those bytes came from the claimed source URL.

## Optional publisher authentication

For cooperating publishers, `source_auth.attest` signs exact source bytes and an HTTPS source identifier. An application with an independently acquired publisher public key can use `source_auth.verify_published_evidence(envelope, source_bytes, attestation, expected_source, pinned_key)` to verify both the contributor's evidence and the publisher's detached signature. No automatic key discovery, URL retrieval or factual adjudication is performed. See TRUST_PROTOCOL.md.

## Local publisher trust management

Load a trusted local JSON policy with `PublisherPolicy.load("policy.json")` from `publisher_policy`. Its schema is openhumanity.publisher-policy.v1, with pins mapping exact HTTPS source identifiers to independently obtained publisher public keys and revoked_keys listing keys to reject. Call `policy.verify(envelope, source_bytes, attestation, expected_source)`. Unknown keys and sources are rejected. Revocation overrides pins; key rotation is manual. Policy files are local configuration and must be protected from unauthorized edits. See TRUST_PROTOCOL.md.

## Publisher-enriched reports

Applications can call `publisher_report.verify_with_publishers(payload, expected_claim_id, policy, proofs)` with a raw signed report, a caller-selected claim ID, a trusted local PublisherPolicy, and a mapping of evidence IDs to `(snapshot_bytes, attestation)` tuples. The result preserves every supplied evidence relationship and separately counts publisher-authenticated evidence. Missing proofs are labeled, invalid proofs are rejected, and truth remains undetermined. The verified client and both optional local model commands also support `--publisher-policy policy.json --publisher-proof EVIDENCE_ID snapshot.txt attestation.json` (repeat the proof option as needed). Only explicitly supplied local proofs are checked, before model context is sent. The commands never fetch snapshots or discover keys automatically.
